# 睡眠积分经济系统设计

状态：2026-09-05 完成 Phase E0、Phase E1 沙盒、Phase E2 测试网审计锚和 Phase E2b 海外测试网铸币演示。Website v1.0（构建 `1.0-website`）与 App 0.15 已实现四维 V2 确定性计分和品牌预付预算人民币兑付申请；官网另已完成 SLEEP 测试代币的合约部署与首笔真实铸币。人民币仍未建立生产可兑付余额，也不产生真实资金转账。

## 1. 产品边界

经济系统明确拆成两条互不混同的路径：

- 中国版使用中心化账本记录平台积分、商城消费和审核后的人民币奖励，不发行代币。Monad 审计合约只保存每日已审核凭证的 Merkle Root。
- 海外演示版把一份服务器已接受的积分凭证映射为 SLEEP ERC-20 测试代币，真实写入 Monad Testnet；当前没有主网、市场价格或流动性。

公链上禁止出现：

- HealthKit 原始样本、心率或睡眠阶段。
- 精确入睡/醒来时间和设备标识。
- 真实姓名、手机号、收款账号或平台用户 ID。
- 可以根据穷举还原个人睡眠记录的无盐哈希。

当前 App 中的“睡眠积分实验”仍只是本地试算，不是积分发行、代币挖矿或人民币兑付承诺。海外铸币入口目前只在官网服务器中实现。

## 2. 计分规则 V2

一个账户在一个“生理夜”只能获得一次奖励。生理夜按本地时区中午 12:00 分界，避免跨零点睡眠被算成两天。

| 睡眠阶段 | V2 阶段积分 |
| --- | ---: |
| 未分期 asleep / Core / 浅睡 | 1 |
| REM | 2 |
| Deep | 1–3，实际睡眠占比 25% 时为 3，向两侧渐变回落 |
| Awake / In Bed | 0 |

有效睡眠最多计 480 分钟。如果当晚可计分阶段超过 480 分钟，按整晚各阶段占比等比缩放，而不是只截取前八小时。

设实际睡眠分钟 `S = asleep + core + REM + Deep`，Deep 分钟为 `D`：

```
depthCloseness = max(0, 1 - abs(4×D - S) / S)
deepWeight = 1 + 2×depthCloseness
durationScale = min(S, 480) / S
stagePoints = round(durationScale × (asleep + core + 2×REM + deepWeight×Deep))
continuity = max(0.70, 1 - 0.02×有效中断次数 - 0.001×内部清醒分钟)
regularity = max(0.70, 1 - 作息偏差分钟 / 600)
awardedPoints = round(stagePoints × continuity × regularity)
```

所有系数在代码和账本中以万分比整数计算，避免 App 与 JavaScript 浮点结果漂移。没有足够多晚数据时，真实本地试算的规律性按中性 `1.0`，不能由单晚推断“长期稳定”；演示页为了让机制可见，使用 21:00–07:00 目标，并把开始/结束时间的环形时钟平均偏差 565 分钟写入明细。

用户授权公开的样例 A 可核对汇总：浅睡 250、REM 50、Deep 105、清醒 31 分钟。实际睡眠 `S=405`，Deep 占实际睡眠 25.9%，有效 Deep 权重 2.926×；阶段分 657、连续性 0.849、规律性 0.700，最终为 **390 沙盒积分**。厂商界面显示的 24.1% 使用包含清醒的 436 分钟作分母；两者口径不同。截图图轴为 457 分钟，未分类的 21 分钟不自行补齐。6 次中断是图中可见片段估计，只有拿到原始逐分钟导出后才能校准。网页按用户本次明确授权展示原始截图，并在四条彩色阶段统计区域加入悬停/点按算法说明；截图不含姓名，但精确日期、时段和健康数据仍可能关联到个人，因此不称为匿名数据，也不代表今后其他用户的截图可默认公开。

本地信任系数仍为：A 厂商签名 100%，B HealthKit + App Attest 90%，C 仅 HealthKit 来源 70%，D 模拟或未验证 0%。这是可版本化的风控策略，不表示 HealthKit 来源已被证明为真实。服务器沙盒积分与产品研究参与补偿是两层不同机制：前者展示个人睡眠质量算法；后者应奖励合格参与，不按健康结果或好评高低付费。正式上线时由服务器保存 `scoringVersion` 与完整 breakdown 并重放计算，App 传来的分数不能直接入账；不同版本不得进入同一 Merkle 批次。

## 3. 真实性证据分层

HealthKit 的来源字段是有价值的溯源信号，但不是硬件签名。App Attest 可以证明请求来自真实 Apple 设备上未被简单篡改的 App 实例，但不能证明佩戴者是谁，也不能单独证明传感器数据真实。

正式系统应组合以下信号：

1. 账户与人的约束：实名兑付时进行 KYC，同一收款人、设备群和风险关联账户设置限制。
2. App 实例：服务器签发一次性 challenge，App 使用 App Attest 对 challenge 和请求摘要作声明。
3. 数据来源：保存 HealthKit source/revision 和样本 UUID 用于去重；若厂商未来提供服务端签名记录，则升级为 A 级证据。
4. 生理合理性：检查时间连续性、阶段冲突、重叠样本、极端重复模式和不可能位移，但不做医疗诊断。
5. 经济风控：新用户延迟结算、单日/单月封顶、异常人工复核、退款/追回记录和全量审计日志。

任何一层都不足以单独等同“真实睡眠”。产品文案应使用“符合当前证据等级”，不应宣称“绝对不可伪造”。

## 4. 多设备与重放防护

- 同一人同一生理夜的多设备样本先按时间区间合并，绝不累加积分。
- 通用 `asleep` 和更具体的 Core/REM/Deep 重叠时，以具体阶段为准。
- Awake 与睡眠同时出现，或同一分钟同时被标为多个具体睡眠阶段时，该区间不计分并进入风险记录。
- 同一人同时佩戴多设备，数据高相关是正常现象，不能单独作弊判定。需要重点检测的是“不同账户之间”长时间存在过度一致的阶段边界、同一样本 UUID/承诺值重复或设备关系群集。
- `nightNullifier = H(serverSecret, accountId, biologicalNight)` 是服务器幂等键，保证一人一夜只入账一次。当前 App 中的 SHA-256 本地 nullifier 只防止本机误操作，不能抵抗卸载、备份恢复或多设备重放。

## 5. 当前 iOS 实现

`SleepEconomy.swift` 完成了不依赖网络的 Phase E0：

- `SleepEconomyEngine`：区间解冲突、8 小时等比封顶、25% Deep 渐变曲线、连续性/规律性系数和信任系数。
- `SleepClaimBuilder`：用 32 字节安全随机盐生成加盐 SHA-256 承诺，原始样本不离开 App。
- `SleepClaimLedger`：在受 iOS 文件保护的本地 JSON 账本中保存草稿，拒绝同一生理夜和同一承诺的重复项。
- `SleepMerkleTree`：对排序后的承诺生成 SHA-256 Merkle Root 和包含证明。叶子前缀 `0x00`，中间节点前缀 `0x01`，防止类型混淆。
- `SleepEconomyView`：显示试算、冲突分钟、可信等级、本地凭证和当前 Merkle Root。

模拟数据的原始分数可以用于界面验证，但信任等级固定为 D，可结算试算始终为 0。

App 0.15 的 `EconomyDemo.swift` 使用系统 `URLSession` 连接公网沙盒，显示服务器积分、V2 四维拆分、虚拟商品、每晚唯一凭证、兑换记录、人民币兑付试点和 Monad 批次；入口位于 App 首页第一屏。App 先使用 `pages.dev` 主线路，失败后自动尝试 `workers.dev`，两条线路均失败才切换为持久化本地演示，并明确标注本地积分不上传、不进入新批次；用户可以手动重连。每台设备只保存一个随机演示账户 ID；页面不会读取或发送 HealthKit 数据，也不持有链上私钥。旧 V1 本地凭证继续兼容读取，新增字段缺失时使用安全默认值，不会因 App 升级而清空可见账本。

### 人民币兑付试点的当前实现

- 资金来源定位为“品牌方预付活动预算”，不把积分包装成可自由交易的代币。
- 服务器用 `CASH_RATE_FEN_PER_100_POINTS` 发布当期汇率，当前为 100 积分 = 100 分人民币；界面展示当期活动浮动范围 ¥0.80–¥1.20/100 积分。
- 报价 `amountFen = floor(points × rateFenPer100Points / 100)`，并与 `quoteVersion`、积分、收款通道和申请时间一起固定保存。金额不使用浮点数。
- 当前状态只能为 `integration_pending`。为避免在没有真实资金和商户通道时制造虚假债权，提交不会扣减积分、冻结可用额或调用支付接口。
- 生产态需把流程升级为 `quoted → reserved → reviewing → paying → paid/failed/reversed`，使用幂等键、双分录账本、签名回调、对账和电子回单；报价只在明示有效期内可预留。
- 启用条件：品牌资金到账；签约主体和企业商户通道开通；用户实名、税务和反欺诈流程完成；对健康数据的特定用途、必要性、单独同意与严格保护完成评审。

演示层为每份睡眠 claim 确定性生成不同的承诺、模拟交易哈希和模拟区块，刷新后保持稳定，用于说明“一晚一凭证”和不可随意改写的产品流程。这些值明确标注为模拟，不会消耗测试币，也不能在浏览器验证。真实链上层继续使用一个固定网络和一个固定审计合约：每个新批次改变 Merkle Root、交易哈希与区块高度。为每个用户或每晚部署新合约既不增加睡眠真实性，也会增加成本和密钥管理风险，因此不采用。

0.11 以同样方式为每笔云端沙盒订单生成独立且稳定的兑换承诺、模拟交易和模拟区块。公开用户操作不得直接调用服务器测试网钱包，否则匿名请求可以持续消耗测试币。生产路线应把已审核订单承诺放入独立的购买 Merkle 批次，由受管理员权限保护的定时任务锚定；链上只保存承诺根、版本、数量和批次类型，不公开商品与用户身份。

## 6. 中心服务器 Phase E1

当前 `server/` 已完成一个 Cloudflare Worker + D1 的演示子集：服务器独立计算模拟分数、账户积分流水、虚拟商品兑换、人民币锁定报价与待接入申请、批次准备、受管理员密钥保护的锚定接口，以及有严格上限的海外测试网铸币接口。它已部署到公网并通过页面/API 实测；但没有生产支付或主网代币能力。

这不等于生产 E1。存在真实付款或商城价值之前，仍必须完成下面的数据流：

```
App 请求一次性 challenge
  → App 读取 HealthKit 并在本地规范化
  → App Attest 绑定 challenge + requestDigest
  → 服务器验证 attest/assertion、去重和风险信号
  → 服务器独立重算分数
  → 写入双分录积分账本
  → 延迟结算 / 人工复核 / 驳回
```

建议的最小接口：

- `POST /v1/attestation/challenge`：签发短期一次性 challenge。
- `POST /v1/sleep-claims`：提交加密传输的规范化样本、来源摘要、承诺和 App Attest assertion。
- `GET /v1/sleep-claims/{id}`：查询 `pending/accepted/rejected/settled/revoked` 状态和不泄露风控规则的理由码。
- `GET /v1/points/ledger`：返回不可改写的借贷分录记录，余额由流水汇总而不是直接修改。
- `GET /v1/sleep-claims/{id}/proof`：返回承诺所在的日批次、Merkle 路径和链上交易引用。

服务器账本至少需要 `accounts`、`devices`、`sleep_claims`、`risk_events`、`point_entries`、`settlements`和 `anchor_batches`。健康原始数据与账户身份应分库/分权限保存，设置最短必要保留期和可审计删除流程。

## 7. Monad 审计锚 Phase E2

`contracts/src/SleepBatchAnchor.sol` 是最小锚定合约：

- 只有 owner 可写入批次。生产环境应把 owner 换为多签或专用发布器，不使用个人热钱包。
- 每个 `batchId` 只能写入一次，保存 `merkleRoot`、`scoringVersion`、`claimCount`和区块时间。
- 合约可验证某个 32 字节承诺的 Merkle 包含证明，不知道对应用户和睡眠内容。
- 链上锚定失败不应阻塞中心积分账本；由定时任务幂等重试，成功后补充交易哈希。

本仓库不保存私钥或管理员密钥。测试网私钥仅保存在 macOS 钥匙串和 Cloudflare 加密 secret；合约地址只有在实际部署成功后才会写入公开配置。主网部署不在当前范围内。

2026-09-04，`SleepBatchAnchor` 已部署到 Monad Testnet，首个只含一份模拟凭证的批次已锚定。RPC 交易回执为成功，交易目标地址与合约一致；再次调用合约 `batches(batchHash)` 读出的 Merkle Root、计分版本和凭证数量与 D1 批次完全一致。2026-09-05，网页和 App 又加入了与真实锚点分开展示的逐晚动态模拟回执。公开证据见 [测试网部署记录](MONAD_TESTNET_DEPLOYMENT.md)。

## 8. 海外铸币 Phase E2b

`contracts/src/SleepRewardToken.sol` 是独立于中国积分账本的最小 ERC-20 兼容测试合约：

- 名称 `MOMO Sleep Test Token`，符号 `SLEEP`，18 位小数；1 个服务器积分映射为 1 SLEEP。
- 只有 owner 可调用 `mintSleepReward`；一份 32 字节睡眠承诺和一个收款地址都只能铸造一次。
- 单笔最多 1,000 SLEEP，合约总量硬上限 20,000 SLEEP；公开服务器另外限制最多 20 笔。
- 链上事件记录收款地址、积分、代币数量和加盐承诺；原始健康数据、身份、设备标识和精确睡眠时间不上链。
- 服务器钱包保存在 Cloudflare 加密 secret，浏览器只提交公开收款地址；D1 保存交易状态与回执，便于失败恢复和公开展示。

合约已经部署到 Monad Testnet，并通过官网完成首笔 390 SLEEP 铸币。链上余额、总供应量、已消费承诺和成功回执均已独立读取核对。该证据证明“铸币动作真实发生”，不证明当前样例来自硬件签名的真实睡眠。SLEEP 虽可在测试网转账，但没有主网价值、DEX/交易所市场或收益承诺；上线海外真实经济前仍需司法辖区选择、代币法律属性、税务、制裁、消费者保护、隐私、经济模型和合约审计。

## 9. 中国发行顺序

1. 先上线不可转让、不可购买、不宣传升值的平台积分，只用于自营商城权益。
2. 人民币奖励与“买币/卖币”完全分离，通过审核后的平台活动规则和合规支付通道发放。
3. 先禁止用户间 P2P 积分交易、付费兑换积分、固定回报或可交易代币，直到中国法律、税务、支付、广告、个人信息和健康数据合规审查完成。
4. 对积分过期、冻结、驳回、退货、兑付封顶和申诉流程给出公开规则。

这是工程风险边界，不是中国法律合规意见。涉及人民币兑付前必须由中国执业律师、税务和支付机构审查。

| 阶段 | 必须达成 | 未覆盖的边界 |
| --- | --- | --- |
| E0 本地 POC | 计分、冲突剔除、模拟零结算、夜间去重、Merkle 证明通过自动测试 | 不证明真实人、真实设备或可兑付 |
